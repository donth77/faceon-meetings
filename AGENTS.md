# FaceOn: guide for coding agents

FaceOn is a free, open-source (MIT), browser-based video meeting app that should feel instantly familiar to anyone who has used Zoom or Google Meet.

## Commands

| Command                                                              | Use                                                                                                                                                                                                             |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm dev`                                                           | Dev server on http://localhost:3000                                                                                                                                                                             |
| `pnpm build`                                                         | Production build (also what Vercel runs)                                                                                                                                                                        |
| `pnpm lint` / `pnpm typecheck` / `pnpm test`                         | ESLint / route types + `tsc` / Vitest; all three run in CI                                                                                                                                                      |
| `pnpm format`                                                        | Prettier (with the Tailwind class-sorting plugin)                                                                                                                                                               |
| `pnpm test:e2e` / `pnpm test:e2e:nightly`                            | Browser tests (Playwright, `tests/e2e`) against `pnpm build`'s output; CI runs the first on every push (see Browser tests)                                                                                      |
| `pnpm stream:setup` / `stream:check` / `stream:lockdown-test`        | Configure Stream (call type, grants, system user), report drift, prove the permission boundary. They use `.env.local`                                                                                           |
| `pnpm cron:setup --url <site>` / `pnpm cron:setup --check`           | Create or update the cron-job.org job that sends reminder emails every 5 minutes / show its latest runs. It reads `.env.production.local` (`CRON_JOB_DOT_ORG_API_KEY`, `CRON_SECRET`) and prints nothing secret |
| `pnpm brand` / `pnpm brand --try <color>`                            | Remake the logo files, icons, link preview, the add-on's Marketplace images (`google-addon/assets/`) and brand colors from `brand/brand.json`, checked for contrast / show what one color gives                 |
| `pnpm desktop:dev` / `desktop:mac` / `desktop:win` / `desktop:icons` | The desktop app (`desktop/`): run it against `pnpm dev`; build, sign and notarize the Mac app on a Mac; build the Windows installer; remake its icons after `pnpm brand`. `desktop/README.md` has every step    |
| `pnpm addon:build` / `addon:push`                                    | A developer's build of the Google Workspace add-on (`google-addon/`) for `FACEON_URL`; build and push it to their own copy with clasp (`google-addon/SETUP.md`). People add theirs from Settings → Calendar     |

Node.js 24 and pnpm 10. Deploys happen by pushing to GitHub (Vercel's Git integration), never with `vercel deploy`. Setting up a copy of your own (accounts, environment variables, migrations, Stream, domains) is in `DEPLOY.md`.

## Architecture map

- `src/app/`: routes (App Router). Metadata files (`icon.svg`, `favicon.ico`, `apple-icon.png`, `opengraph-image.png`) live here, with the web app manifest (`manifest.ts`) and the page the service worker shows offline (`offline.html/route.ts`, self-contained because the worker keeps a copy). `[locale]/j/[code]` is the meeting page; `api/meetings/[code]/` holds the meeting API: the ID lookup itself (GET, so the Join field can say there's no such meeting without leaving the page; it counts misses like the meeting page), `join`, `token`, `end`, `hand`, `moderate` (host controls), `notes` (AI notes on or off, for hosts, where the meeting's host allows them), `notes/[sessionId]` (save, share or delete a session's AI notes), `lobby` (the waiting room, for hosts), `admission/[requestId]` (asking to join) and `seen` (the meeting page says when someone leaves, so a session nobody's in ends then, not when it's next noticed). `api/integrations/google-calendar` says where the caller's Google Calendar stands (`GET`, which the desktop app watches while someone connects it in their browser) and disconnects it (`DELETE`). `api/desktop/upcoming` lists the next day's meetings for the desktop app's reminders. `api/integrations/google-addon` adds, updates and removes the caller's own copy of the Google Workspace add-on (`POST` `{ action }`, `DELETE`), and says where it stands (`GET`, which Settings → Calendar asks again on focus, and the desktop app while someone adds it in their browser). `api/addon/google/` is the add-on's API: `conferences` (FaceOn meeting for a Calendar event; PATCH and DELETE follow the event), `meetings` and `home` (the side panel), each authenticated by the person's Google identity token from their own copy. `api/history/[sessionId]/attendance` and `api/history/[sessionId]/notes` are what a past meeting's Download menu in Previous offers (attendance as CSV, for its host; the saved AI notes with their transcript as Markdown, for whoever may read them), `api/history/export` is Previous's "Download history" and `api/account/export` Settings → Account's "Download your data" (both zips made on request, sharing a few downloads per account every ten minutes). `api/health` is for uptime monitors (`?db=1` also checks the database, at most once a minute), and `api/csp-report` takes the Content Security Policy's reports. `instrumentation.ts` and `instrumentation-client.ts` start error reports where `NEXT_PUBLIC_SENTRY_DSN` is set (Sentry or GlitchTip; the browser loads it once the page is idle, and `lib/monitoring/scrub.ts` takes out anything about the person first).
- `src/lib/`: server and shared logic.
  - `hosting/`: who hosts full meetings beyond the operator's settings. The admins' list of approved addresses (`allowlist.ts`), requests to host full meetings and their answers (`requests.ts`), the plan with both counted (`access.ts`, `hostingPlanOf`), the emails about them (`emails.ts`), and the pure rules (`rules.ts`). Settings → Admin (`app/[locale]/(app)/settings/admin`; the old `/admin` redirects there, `components/admin/`) is for admins only and does nothing else: each action in `admin-actions.ts` checks the caller is an admin, and none can change, delete or see into an account. Its lists are paged on the server, each list's page in the address (`lib/pagination.ts`, `components/ui/pager.tsx`). Next.js renders a page anew when its search params change, so the loading state is in `settings/admin/layout.tsx` and the page exports `instant = false`: the current page stays on screen until the next is ready.
  - `env.ts` (public) and `server-env.ts` (server-only) validate environment variables with Zod.
  - `auth/`: Better Auth (`server.ts`, `client.ts`, `session.ts`; `desktop-handoff.ts` signs the desktop app in through the browser, with a one-time token for a PKCE-style challenge from `lib/desktop/handoff.ts`, then a session of the app window's own; `/desktop/sign-in` is its page), the origins sign-in trusts (`origins.ts`: production, the deployment's own address, never a wildcard), password rules and error mapping. Email accounts must verify their address; responses never reveal whether an email has an account.
  - `email/`: account emails through Resend (`send.ts`; in development they print to the server log) and their localized templates.
  - `reminders/`: email reminders before meetings, opt-in in Settings → Notifications (`user.email_reminders`: how long before, and the time zone the emails use). Which reminders are due and the daily cap (`rules.ts`, pure and unit-tested), the email, modelled on Zoom's invitation (`email.ts`), sending them once each (`send.ts`, with `reminder_sent` records the sweep prunes after two days), and the signed link that turns them off (`token.ts`, with `/unsubscribe` asking first and `/api/email/unsubscribe` for mail apps' one-click). `/api/cron/reminders` runs it every 5 minutes, called by cron-job.org (`pnpm cron:setup`), since Vercel's free crons run daily; it and `/api/cron/sweep` check `CRON_SECRET` (`lib/cron.ts`).
  - `guest-session.ts`: the signed guest cookie (a random guest ID and avatar, no personal data; the avatar is the one the join screen showed). `avatars/`: default avatars' seeds (`seed.ts`), the look a first name suggests for a default (`name-look.ts`; browsers load it only for a first-time guest) and an account's avatar or sign-in photo (`account.ts`). `rate-limit.ts`: fixed-window counters for failed attempts, keyed by a hash of the IP address, never the raw address. `log.ts`: errors for the server log without a failed query's values. `uuid.ts`: IDs from URLs are checked before any query.
  - `db/`: the database client (`index.ts`), waking a sleeping database as someone shows intent (`wake.ts`, `wake-rule.ts`; the page side is `components/app-shell/wake-on-intent.tsx`, the route `/api/wake`), and the Drizzle schema (`auth-schema.ts` is generated by Better Auth; `meetings-schema.ts` is ours). Migrations live in `drizzle/`.
  - `meetings/`: meeting IDs and passcodes, and reading what someone typed or pasted into the Join field (`codes.ts`), the join and moderation rules (`rules.ts`, pure and unit-tested: who gets in and as what, including co-hosts a meeting names ahead of time by email (`meeting_invitee.cohost`), and the host-controls permission matrix), the join flow (`join.ts`), admitting someone (`admission.ts`, the only place media tokens are minted), the waiting room (`waiting-room.ts`), host controls (`moderation.ts`), AI notes on and off, including meetings that start them automatically (`notes.ts`), saved AI notes and who may read them (`saved-notes.ts`), the session's shared state (`session-state.ts`: hands, roles, spotlight, policies and whether AI notes are on (or were stopped), written under a per-session lock), session lifecycle (`sessions.ts`), the hosting policy (`hosting.ts`: approved hosts get full limits, everyone else demos; `isAdmin` is `ADMIN_EMAILS` only), how long records are kept (`retention.ts`, as the privacy policy says) and the housekeeping sweep that enforces it (`sweep.ts`, run daily by Vercel Cron at `/api/cron/sweep`), Previous (`history.ts`, with who came worked out in `attendees.ts`; `pastSessions` is shared with exports), queries, the API's request/response types (`api.ts`, shared with the client) and server actions (the schedule form's signed draft is made in `schedule-draft.ts`, which is server-only, never an action; the options a host last scheduled with, which the next meeting starts from, are kept on their account, `user.schedule_defaults`, and read and merged in `schedule-defaults.ts`).
  - `exports/`: the downloads people make of their own data. Pure builders, unit-tested: spreadsheet-safe CSV (`csv.ts`: a byte-order mark, quoting, and text that looks like a formula kept as text), attendance rows and whose email they show (`attendance.ts`: only people the host invited, and the reader's own), the files of "Download history" (`history-files.ts`) and "Download your data" (`your-data-files.ts`), built from shared pieces (`files.ts`: README, attendance table, notes with their transcripts) and zipped as they're read (`zip.ts`, fflate). The server side gathers them (`attendance-data.ts`, `history-data.ts`, `your-data.ts`: never sign-in tokens or password hashes), words them in the reader's language (`labels.ts`) and keeps one download budget (`limits.ts`).
  - `media/`: the media-provider interface (`types.ts`, including `CameraProcessor` and `MicrophoneProcessor`, which a provider's client runs on the camera or the microphone before anything is sent), the provider registry (`index.ts`) and the voice meter adapters use for speaking rings and voice bars (`voice-meter.ts`, its rules in `voice-activity.ts`): each person's voice measured from their audio in the browser, because a media server's speaking events arrive up to a second late. `stream/` is the Stream adapter (its webhook is parsed in `webhook.ts`); a LiveKit adapter will sit beside it. Hosts' browsers get the same Stream grants as everyone's: host controls go through our API (`scripts/setup-stream.ts`, proven by `stream:lockdown-test`).
  - `device/`: browser device helpers (permission problems, remembered devices, test sound).
  - `capabilities.ts`: what this browser and device can do, in one place: joining calls (WebRTC), the camera and microphone, picture-in-picture (and opening it by itself), screen sharing and Chrome's share options, choosing a speaker, full screen, strong noise suppression, backgrounds and motion backgrounds, notifications (or notifications once on an iPhone's Home Screen) and a keyboard. Components read them with `useCapability` (`hooks/use-capability.ts`), which matches the server's HTML while a page hydrates.
  - `notes/`: AI notes, made in the browser: speech to text on each person's own device (`speech.ts`), whether this browser can do that and the one-time download it may need first, shared by the room, pre-join and Settings → AI notes (`speech-setup.ts`), the notetaker's transcript, in blocks by speaker, pause and length, and the notes made from it (`transcript.ts`, kept only in that tab), the notes' shape, prompts and Markdown (`notes.ts`), making them on-device or with the host's own key (`engines.ts`, `providers.ts`: the five providers, called straight from the browser) and Settings → AI notes (`settings.ts`). Whether a host's meetings offer AI notes at all is an account setting, off to start (`user.ai_notes`, `allowNotesInMeetings` in `lib/meetings/notes.ts`), copied into each open session so co-hosts are held to it too.
  - `ai/`: Chrome's built-in model through the Prompt API (`built-in.ts`), shared by Help's assistant and AI notes.
  - `effects/`: backgrounds and effects, processed on the device: the choices and how they're stored (`effects.ts`), the engine (`engine/`: MediaPipe's selfie segmenter finds the person (its usage reports to Google are stopped in `segmenter.ts`), a guided filter lines the mask's coarse edges up with the camera image, and a WebGL2 compositor draws the blur, picture or video behind them; it loads only when a camera has an effect), the processor the room hands to the media provider (`camera-effects.ts`), and backgrounds people add, kept in their browser (`uploads.ts`). Nobody receives the camera unprocessed while an effect is on: if one can't run, the video goes off.
  - `google-calendar/`: Google Calendar sync, for hosts who connect it in Settings → Calendar (Better Auth's `linkSocial` adds the `calendar.events.owned` scope; sign-in never asks for it). The scopes (calendar, and the add-on's `script.projects`) and shared types (`shared.ts`), where someone's connection stands, their access token for either scope (refreshed by Better Auth; `refresh.ts` notices when Google refuses the grant, which means reconnecting) and letting go of a scope, which revokes Google's grant only when the other one doesn't still use it (`connection.ts`), the Calendar API client (`api.ts`), the events a meeting should have (`events.ts`: one per one-off meeting or series rule, with one-off changes as changed or cancelled occurrences), and the sync that brings the host's calendar in line after each save (`sync.ts`, `reconcile.ts`). A synced meeting keeps its event IDs in `meeting.google_events`; Google emails the invitees.
  - `noise/`: noise suppression on the microphone (Settings → Audio): off, standard (the browser's own, the default) or strong: RNNoise in an AudioWorklet on the device (`engine.ts`, loaded only when a microphone needs it), handed to the media provider as a `MicrophoneProcessor` (`microphone-noise.ts`). Where strong can't run, or stops working, the browser's own takes over and people are told once (`support.ts`).
  - `preferences.ts`: Settings kept on this device (time format and zone, noise suppression, mirroring, HD, single-key shortcuts…) and `useIntlLocale()`, the locale every date and time is formatted with. `withDefaults()` gives settings as they act (with Notifications off, every sound, pop-up and reminder is off); `chosenSettings()` gives them as chosen, for Settings to show.
- `src/components/auth/`: sign-in, sign-up, verification and password-reset screens. `marketing/` holds the public header (one layout for every signed-out page), footer and language menu; `help/` the Help pages; `settings/` the Settings sections (also shown in the meeting's Settings dialog); `notes/` the AI notes view, the flow that makes and saves them (in the meeting's panel and after leaving), the saved notes page (`/previous/<session>/notes`) and the one-time speech download (pre-join and Settings); `shortcuts/` the Keyboard shortcuts dialog (`?` anywhere) and the list it shares with Settings → Accessibility; `effects/` the backgrounds and effects picker with its live preview (pre-join, the meeting's panel, Settings); `device/` what pre-join, Settings and the meeting share about your camera and microphone (the mirrored preview, the local track, the mic meter, the problem note and the Audio and Video switches); `avatars/` the avatar picker Settings → Account and the join screen share; `google-calendar/` connecting Google Calendar from a form (in a consent window that reports back; in the desktop app, in the browser through `/desktop/calendar`, straight to Google's consent), the schedule form's "Add to my Google Calendar" row, and what Google Calendar did after a save, with Retry or Reconnect.
- `src/components/meeting/`: the meeting client, loaded only in the browser.
  - `meeting-entry.tsx`: pre-join → waiting for the host, or asking to join → room → left. `pre-join/` is the join screen: the preview, your avatar beside your name (`join-avatar.tsx`: the one you join with; a guest's travels with the join request into their cookie, an account's is saved to it), the passcode when the meeting will ask for one (the page works it out on the server, as `passcodeNeeded` in `rules.ts` does), and the meeting's own Settings dialog (`room/in-call-settings.tsx`, which takes the preview's devices before the room exists).
  - `media.tsx`: the client media port (`useRoomMedia()`, `<TrackView>`); `room/` is our UI on top of it. Voices change many times a second, so they aren't in the participant list: `useSpeaking`, `useAudioLevel` and `useDominantSpeakerKey` let just the component that shows one follow it, and adapters keep room media the same object until something it shows changes (`lib/reuse.ts`). Roles and policies come from the session's shared state (`room/roles.ts`); host actions call our API, never the media SDK, and the ⋯ menu offers what `canModerate` (`lib/meetings/rules.ts`, shared with the server) allows.
  - `room/meeting-shell.tsx` lays the room out; its parts live in hooks beside it: `use-panels.ts` (side panels, and where focus goes as they open and close), `use-auto-hide.ts` (on a phone, the controls float over the video and step aside after a few seconds; the rules are in `controls-visibility.ts`, and `controls-layer.tsx` holds the layers and what shows while they're away), `use-meeting-notes.ts`, `use-reactions.ts`, `use-hands.ts`, `use-screen-share.ts` and `use-room-alerts.ts`.
  - `room/stage.tsx` places the tiles (Auto, Gallery, Speaker, Spotlight, and a one-on-one with you floating in the corner); what shape and size each tile takes (a camera is never cropped by more than a fifth, a shared screen never at all) and where the strip goes beside a large tile are worked out in `stage-layout.ts`, from the shape each picture reports.
  - `providers/stream/`: the Stream bindings. Rooms load their provider's bindings on demand.
- `content/help/<locale>/`: the Help articles, one Markdown file each with front matter (`title`, `summary`, `category`, `order`). Write `{appName}` for the app's name, and the limit placeholders (`{demoPeople}`, `{fullLength}` and the rest, in `src/lib/help/placeholders.ts`) for this copy's meeting limits, as `meeting-limits.md` does. A language without its own folder shows English. `src/lib/help/` reads them; `/help` lists and searches them, and `/help/<file name>` shows one. Search folds case and accents the same way everywhere (`lib/help/text.ts`). An article opened from a search gets the search as `?q=` (`helpArticlePath`) and highlights it: the matching is pure (`lib/help/highlight.ts`), and `components/help/help-highlights.tsx` marks the article's text and shows the match bar.
- `content/legal/`: the privacy policy, the terms and the credits (`/privacy`, `/terms`, `/credits`), in Markdown with front matter (`title`, `updated`). The credits name everyone whose work FaceOn uses (avatars, backgrounds, the segmentation model, fonts and icons); a unit test checks every background's maker is there, so add a line when a background or credited asset is added. `src/lib/content/legal.ts` fills in `{appName}`, `{siteUrl}`, `{operator}`, `{contact}` and `{governingLaw}` from the operator settings in `.env.example`, so a self-hosted copy names itself. Keep them true to what the code does: when a feature changes what's kept or who handles it, update the privacy policy and its `updated` date. Sign-up, sign-in and a guest's pre-join link to both (`components/legal/`).
- `src/lib/security/`: the Content Security Policy (`csp.ts`: every host the browser may reach; next.config.ts sends it report-only until `CONTENT_SECURITY_POLICY=enforce`), reading its reports (`csp-report.ts`), and addresses and text made safe for logs and error reports (`redact.ts`: no query strings or fragments, IDs in paths replaced).
- `src/lib/human-check/`: Cloudflare Turnstile, where both its keys are set. Better Auth's captcha plugin checks the requests that send email (sign-up, password reset, the verification email again); the join route checks a new guest's first join (`verify.ts`). Its text is messages' `GoogleAddon` section. Nobody publishes it: each person adds their own copy from Settings → Calendar, and installs it with one click in Google's Apps Script editor. Copies are `google_addon` rows, one per person. Meetings made from Calendar are `meeting.origin = 'google_addon'` with `google_addon_event`; Calendar sync leaves them alone, and their time is changed in Google Calendar. `SETUP.md` is the developer's guide and `QA.md` the checklist before a change. Vercel builds add-on changes too, since the server writes the add-on into people's accounts (and always builds a commit whose message starts with "Redeploy:", the empty commit that applies changed settings).

It's a thin shell around the hosted app: `src/main/` holds the window, the rules for what it may load and which permissions it grants (`policy.ts`, `security.ts`), `faceon://` links (`links.ts`), the bridge's main side with every call checked by Zod (`ipc.ts`, `schemas.ts`), sign-in through the system browser, the tray, the mute shortcut, the share picker, reminders, the badge and updates. `src/preload/preload.ts` exposes `window.faceonDesktop` on the app's origin only. Its contract is `src/lib/desktop/bridge.ts`, which the shell imports for types only; the web app finds it with `useDesktop()` (`src/lib/desktop/use-desktop.ts`) after hydration, since the cached shell is the same for everyone. In browsers, `lib/desktop/open-in-app.ts` decides the join page's **Open in the FaceOn app** (only where the browser knows the app is here, from signing it in; Settings → General's Ask each time, Always or Never), and `lib/desktop/releases.ts` reads the latest release (`DESKTOP_RELEASES_REPO`; each installer by its fixed name, `lib/desktop/downloads.ts`, which also tells the device apart, and through `releases/latest/download/<name>` when GitHub's API can't be asked) for `/download` and the **Download for Windows** or **Download for Mac** buttons, which show only on that computer, after hydration (`useDesktopDownload`). ## Conventions

- **TypeScript strict.** Validate every boundary (env, request bodies, webhooks, custom events) with Zod.
- **Secrets stay on the server.** Only `NEXT_PUBLIC_*` values may reach the browser. Server modules that read secrets import `server-only`.
- **The Content Security Policy lists every host.** Anything new the browser loads or calls directly (a script, an API, an image host) goes in `src/lib/security/csp.ts`, or production's reports, and later browsers, will turn it away.
- **Hosts' AI keys never reach our server.** They're kept in the host's browser and sent only to their AI provider; no route accepts, stores or logs them.
- **Media SDKs only in adapter folders.** `@stream-io/*` and `livekit-*` may only be imported inside the media adapter folders. UI code talks to the provider-neutral interface.
- **UI text.** Every user-facing string comes from the message files, including `aria-label`s, tooltips and screen-reader announcements: English first; es, pt-BR, fr, de and ja follow. Format dates, times and numbers with `Intl`; `lib/time.ts` has the shared helpers (days, time ranges that cross midnight, lengths of time such as "1 hr, 15 min").
- **The app's name.** Messages say `{appName}`, not FaceOn, with `appName: publicEnv.NEXT_PUBLIC_APP_NAME` passed where they're shown, so a copy's own name shows everywhere. Only credits for work made for FaceOn keep its name.
- **Brand colors.** Use the tokens (`primary`, `ring`, `secondary`, `chip`…), never the brand's hex values, so `pnpm brand` restyles everything. Brand-colored text on the tint (`bg-secondary`, `bg-accent`, `bg-chip`) is `text-chip-foreground`; `text-primary` there is for icons only.
- **Familiar words.** Use the words Zoom and Meet users know: Mute / Unmute, Start video / Stop video, Share screen / Stop sharing, Participants, Chat, Raise hand / Lower hand, Waiting room, Admit, Leave meeting, End meeting for all, Meeting ID, Passcode.
- **Icons.** Lucide first; another open-licensed set in the same style only when Lucide has no fit.
- **Accessibility.** WCAG 2.2 AA in light and dark themes: real buttons with labels, visible focus (the `focus-ring` utilities), keyboard access, and tooltips that also appear on focus. When a control removes itself or a screen changes, move focus somewhere sensible first.
- **Browser support.** A feature that depends on the browser or device asks `lib/capabilities.ts`: it's hidden where it can never work, and shown disabled with a reason only where something on this device can make it work (a permission, a download, adding the app to the Home Screen). A saved choice the browser can't run falls back quietly. Help says where each such feature works.
- **React Compiler.** It's on (`reactCompiler` in next.config.ts), so components and values are memoized for you: write plain code, and reach for `useMemo` or `useCallback` only where an effect or an external store needs a stable identity. It assumes module-level variables never change, so a function that changes one belongs at module level, outside any component or hook (see `lib/pwa/install.ts`).

## Browser tests

- **Where:** `tests/e2e/*.spec.ts`, with helpers in `tests/e2e/support/`. `people.signedIn()` and `people.guest()` give each person a browser of their own, and `createMeeting`, `createPastMeeting` and `needsStream()` set the scene. Their camera and microphone are `tests/fixtures/cam.y4m` and `mic.wav` (synthesized). Meeting tiles carry `data-tile`, `data-name` and `data-local` for finding a person's video.
- **Who's signed in:** tests write their own users and sessions to the database and sign the session cookie with `BETTER_AUTH_SECRET`, so only the sign-in tests use the sign-in screens. Every test's users are unique and deleted afterwards, along with what they host.
- **Which database:** the one in `E2E_DATABASE_URL` (or the app's own). The tests refuse a production deployment, the database `.env.production.local` names, and any database off this machine unless `E2E_ALLOW_REMOTE_DATABASE=1`. CI uses a Postgres container that's thrown away.
- **Running them:** `pnpm build` with `NEXT_PUBLIC_APP_URL=http://localhost:3100`, then `pnpm test:e2e`, which starts the build on port 3100. With `.env.local`'s development database: `E2E_ALLOW_REMOTE_DATABASE=1 pnpm test:e2e`. The server it starts has no email delivery, OAuth apps or approved hosts, as in CI: nothing reaches a real inbox, and every test account hosts demo meetings. Tests that join calls need Stream's development keys, and are skipped without them.
- **Writing one:** find things the way people do (by role and label), wait with `expect` rather than fixed pauses, end with `expectNoErrors`, and tag slow or Firefox-only tests `@nightly` (and `@firefox`).

## Definition of done

- Typed, with no `any` leaks.
- Tests are added: unit tests for logic, and a browser test in `tests/e2e` for anything people do on screen.
- Works at 375 px and 1440 px.
- Keyboard accessible, with visible focus, in light and dark themes.
- All UI text comes from the message files.
- No console errors.
- README, DEPLOY.md, AGENTS.md and `.env.example` are updated when behavior or configuration changes.
